# 翻译成本治理 — 规格 v1

> 版本 v1 / 2026-10-11 / 档位 M / 读者：book-agent 维护者与产品负责人 / 前置：无 / 状态：**待裁决**
>
> 起点是用户的需求："提高输入缓存（prompt cache）命中率，以降低平均翻译成本"。审计和实验的结论是：命中率已经接近这套提示词结构的上限；钱主要花在输出 token 和高峰时段上；成本记账本身也有错。

## 0. 一屏摘要

**最重要的 3 个发现**

1. **成本记账错了，而且多记了。** 系统存的非高峰时段是 `16:30-00:30` UTC（`provider_credentials.off_peak_window_utc`），只有一个窗口。DeepSeek 现行价目页的规定是：工作日 01:00–04:00、06:00–10:00 UTC 为高峰，其余时间（含整个周末）都是非高峰，非高峰价格为高峰的一半。按现行规则重算近 14 天的 10,481 次调用：记录是 $6.583，实际约 $5.355，**多记约 23%**。预付额度按这个数扣费（`services/prepaid_credit.py:94`），所以用户被多扣了。
2. **输入缓存命中率已经约 80%，接近结构上限。** 实测（真实调用，读取 API 返回的 `prompt_cache_hit_tokens`）：顺序 83.1%、并发 78.5%、先预热再并发 80.1%（各 8 次）。相邻分组的提示词有约 93% 的字符前缀相同，因为两段 system 在前、每个分组的内容在后，已经是对缓存友好的顺序。命中率从 80% 提到 90%，总成本只降约 15%，而且没有已知手段能稳定做到。
3. **钱主要花在输出上，而输出有一半是重复内容。**
   - 输出占成本 66%，未命中的输入占 32%，命中的输入只占 2.6%。
   - 翻译调用返回的 `alignment_suggestions` 是对 `target_segments[].source_sentence_ids` 的重复，`packet_id` 是把题目里的 UUID 原样抄一遍。同样 10 个分组去掉这两项后，输出 token 从 2,432 降到 1,256（**−48%**），句子覆盖完整，译文差异落在模型自身的随机波动内（对照见 §4）。
   - 润色调用要求"每一段都要返回"。近 3 天 6,409 次润色里，49% 一个字都没改；其余的回包里约 36% 是原样照抄。估计润色输出约 2/3 是重复。

**已经被推翻的假设**

- "提示词结构不利于缓存，调整顺序就能大幅提高命中率"：不成立，前缀已经共享约 93%。
- "多个 worker 并发冷启动是主要的未命中来源"：基本不成立，各方案只差约 5 个百分点（n=8，在噪声范围内）。
- "命中和未命中的 token 拿不到，只能从费用反推"：不成立，API 每次都返回，是我们丢掉了（`workers/llm_calls.py:36` 的 `usage_payload` 不写这两个字段）。

**M0 做什么：** 修正高峰/非高峰的计价规则（多个窗口、按星期几），把命中和未命中 token 写进调用记录，并给出历史多扣费用的处理方案（待裁决）。

**需要用户裁决：**

1. 历史上多记的成本和多扣的预付额度怎么处理：只修正以后，还是补一份更正对账单并退回额度？
2. 是否提供"非高峰运行"选项：白天提交的书排到非高峰时段再翻，预计省约 32%，代价是要等。
3. 字面需求和诊断的分歧（§2.6）：确认把重点从"提高命中率"改为"减少输出、改进调度、修正记账"。

### 1.4 已证伪清单

- 调整提示词顺序以大幅提高命中率（E1/T5：已共享约 93% 前缀）。
- 并发冷启动是主要未命中来源（E1：差别约 5 个百分点，在噪声内）。
- 不要重新引入"从 cost_usd 反推命中率"：API 直接给了。
- 润色本身是有效的，不能删：上线前在 48 段盲评中 20:10 胜出（`polish.py` 模块文档）。本规格只削减它的重复输出，不动润色本身。

## 2. 问题定义

### 2.1 核心问题

每本书的翻译花费中，约一半花在模型把我们已知的东西再抄一遍上（UUID、对齐映射、没改的段落），另有约 64% 的花费发生在价格翻倍的时段。同时，系统给用户记的账比实际多约 23%。成功的定义：同样质量下，每千字原文的实际成本下降，并且账单与供应商计价一致。

### 2.2 决策时刻

- **用户：** 提交一本书时决定"现在翻"还是"便宜地翻"；看对账单时判断余额够不够。
- **维护者：** 看每本书的成本拆分（输入命中/未命中/输出、高峰/非高峰），决定下一步优化什么。

### 2.3 北极星

`每千字原文实际成本 = Σ cost_usd(按供应商现行规则计价) / (原文字数 / 1000)`

基线：按 M0 修正后的计价，取《The Art of AI》全书运行重算。目标是 M1+M2 后下降 ≥30%，M3 对白天提交的书再降约 30%（估算，见 §4）。

### 2.4 隐含需求

1. 账必须对：用户是预付的，多扣钱比贵一点更伤信任（D1）。
2. 省钱不能牺牲质量：润色是经过盲评的改进，要保留它的修改，只省掉重复。
3. 要能看见命中率和成本拆分，否则以后无法判断优化有没有效（D2）。
4. 等待的代价由用户自己选：非高峰运行必须是选项，而且要说清楚什么时候开始、能省多少。

### 2.5 非目标

- 不更换模型或供应商，不选支付渠道（AGENTS.md），不凭记忆报价。
- 不调整提示词顺序（已证伪），不做缓存预热（收益不足以证明）。
- 不改翻译的规则内容和译文风格。
- 不处理中国法定节假日（价目页说节假日算非高峰，本版不建节假日日历，偏差是少算节假日的优惠，即保守多记）。

### 2.6 字面需求与诊断的分歧（待裁决）

- **字面需求：** 提高输入缓存命中率来降低成本。
- **诊断：** 命中率已约 80%。就算到 90%，总成本也只降约 15%，而且没有可验证的手段。按估算，减少输出能降 35–40%，非高峰调度能降约 32%，修正记账则是用户实际付的钱减少约 23%。

本规格按诊断安排里程碑，但 M0 会先把命中率变成可监控的指标，以后命中率下降时能看到。

## 3. 设计哲学

### 3.1 失败考古

1. **只优化看得见的指标。** 表象：命中率提高了，账单没怎么变。根因：命中的输入本来只占成本 2.6%。诱因：缓存命中率是厂商宣传最多的指标。早期信号：先算一下成本构成。防御：北极星用实际成本，不用命中率。
2. **相信自己的记账。** 表象：省钱措施的效果算不准。根因：计价规则过时（D1）。防御：计价规则做成带日期的配置，并定期对照价目页（§8.5）。
3. **为省钱砍掉质量环节。** 表象：直接关掉润色，看起来省 44% 的输出。根因：没区分"必要输出"和"重复输出"。防御：只去掉可以从已知信息推出的输出。

### 3.2 平庸与顶尖的分界

平庸的做法是在已经被优化过的维度上继续压缩。顶尖的做法是先问"模型输出的每个 token，我们是不是本来就知道"：模型只该生成我们不知道的东西，比如译文和改动；其余（ID、映射、未改段落）由程序推出。

### 3.3 范式转换

不写。本规格是修正确性，再去掉重复输出。

### 3.4 跨域移植

【工具借用】网络协议里的增量传输（只发差异，接收方按已知状态还原），用于润色只返回改动段落。

### 3.5 保留什么 / 丢弃什么

- **保留：** 两段 system 在前的提示词结构、润色的编辑规则、输出 JSON 的 target_segments（含 source_sentence_ids）。
- **丢弃：** 回包里的 packet_id、alignment_suggestions，以及润色回包里没改动的段落。

### 3.6 诚实的边界

本系统不是质量评估器。它只保证去掉的输出可以从已知信息还原，译文质量的判断仍然靠分层 QA 和盲评。

## 5. 设计决策记录

**决策 1：计价规则改为"高峰时段表"**
- 选择：配置写成一组 `{星期几, 开始–结束 UTC}` 的高峰窗口（默认为 T2 的规则）。
- 替代方案：继续用单个非高峰窗口。
- 理由：D1；现行规则无法用单窗口表达。
- 代价：配置格式迁移，要兼容旧值。
- 逆转条件：供应商取消分时计价。

**决策 2：命中/未命中 token 写入调用事件**
- 选择：`usage_payload` 增加 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`（D2）。
- 代价：事件变大约 40 字节。
- 逆转条件：无。

**决策 3：回包去掉 packet_id 和 alignment_suggestions，对齐边由 target_segments 推出**
- 选择：程序已知 packet_id，不再要求模型抄写。对齐关系由每段的 `source_sentence_ids` 推出：一段对一句是一对一，一段对多句是多对一，一句被多段引用是一对多。
- 替代方案：保留 alignment_suggestions 但缩短字段名。
- 理由：E4（输出 −48%）、T11（下游需要的信息都能推出）。
- 代价：要改校验（output_validation）和建边（services/translation.py 三处），老格式仍需能解析（兼容期）。
- 逆转条件：M1 盲评或 QA 显示质量下降，或对齐失败（ALIGNMENT_FAILURE）增加。

**决策 4：润色只返回改动的段落**
- 选择：`{"segments": [...只含改动的段落...]}`，没改动时返回空数组，未返回的段落保留原译。
- 替代方案：返回全部段落（现状）。
- 理由：E5。
- 代价：模型可能漏返回本该改的段落，所以要监控改动率。
- 逆转条件：改动率比现状下降超过 10 个百分点（说明模型被"可以不返回"诱导偷懒），或盲评质量下降。

**决策 5：非高峰运行做成用户选项，不默认开启（待裁决）**
- 理由：E6，省约 32%；但等待时间由用户决定。
- 逆转条件：用户选择默认开启。

## 6. 架构与模块

### 6.1 改动全景

```
pricing.py ──高峰时段表──▶ _estimate_cost_usd（M0）
llm_calls.usage_payload ──+hit/miss──▶ events（M0）
translator 契约 / openai_compatible._build_payload ──去 packet_id/alignment──▶ 回包（M1）
output_validation + services/translation 建边 ──由 target_segments 推出──（M1）
polish.py 提示词 + 合并逻辑 ──只返回改动──（M2）
runs：提交时可选"非高峰运行"→ 队列在高峰期暂停领取（M3，待裁决）
```

### 6.2 模块要点

- **pricing：** `peak_schedule_utc`，例如 `"mon-fri 01:00-04:00,06:00-10:00"`；旧的 `off_peak_window_utc` 继续可读。单测覆盖每个窗口边界、周末、跨午夜。
- **usage_payload：** 增加两个字段；读取方（对账单）把缺失视为未知，不当作 0。
- **回包精简：** 去掉回包里的 packet_id 后，由调用方在解析时填入。alignment 在解析阶段从 target_segments 生成，下游代码不变。兼容期内仍接受老格式。单测：一对一、多对一、一对多、句子漏覆盖要报错。
- **润色增量：** 提示词改为"只返回你修改过的段落；没有修改就返回空数组"；合并时没返回的段落沿用原译；回包里出现未知编号就整次作废。审计字段 `changed_segments` 保留。

### 6.3 数据模型

不加列。events payload 是 JSON。provider_credentials 增加 `peak_schedule_utc`（text，可空，按项目的 schema 自动同步规则）。

## 8. 验证方法

### 8.1 评估目标

用户为同一本书付的钱更少，账与供应商一致，而译文质量不降。

### 8.2 指标

- 每千字成本（北极星）。
- 每次调用的输出 token（翻译、润色分开统计）。
- 命中率 = hit / (hit + miss)，健康区间 75–90%，低于 70% 报警。
- 润色改动率 = 有改动的润色次数 / 润色次数，基线 51%。
- ALIGNMENT_FAILURE 数量，基线为当前值。

### 8.3 协议

M1/M2 各用两章做 A/B 试译（同一章分别用旧格式和新格式）：
- 分层 QA 的阻断和重要问题数不增加；
- 盲评 ≥40 段，新格式不劣于旧格式（新格式输的段数不超过赢的段数 + 5）；
- 对齐失败为 0。

### 8.4 反自欺清单

- 相似度不是质量：必须盲评。
- 先跑"旧格式对旧格式"的对照，估计随机波动。
- 输出降了不等于钱降了：用修正后的计价算总成本。
- 润色改动率要和基线 51% 比较，防止模型因为"可以不返回"而少改。

### 8.5 上线后健康监控

- 每周对照一次价目页的高峰规则（人工或脚本）；计价配置写明核对日期。
- 命中率和每千字成本按书展示，异常时在成本页提示。

## 9. 里程碑

- **M0（正确性，一个会话）**：高峰时段表、调用事件写入命中/未命中、修正后的成本对账脚本（列出历史多记金额，是否退回待裁决）。验收：单测覆盖窗口边界；重算 14 天与 §0 的数字一致；新调用的事件里有 hit/miss。
- **M1（回包精简，一个会话 + 一次 A/B）**：验收：翻译输出 token −35% 以上，QA 和盲评不劣，对齐失败为 0。依赖 M0（需要准确计价才能比较成本）。
- **M2（润色增量，一个会话 + 一次 A/B）**：验收：润色输出 token −50% 以上，改动率在 51% ± 10 个百分点内，盲评不劣。
- **M3（非高峰运行，待裁决）**：提交时可选；队列在高峰期不领取新分组；界面显示预计开始时间和预计节省。验收：白天提交、选了非高峰的书没有一次调用落在高峰。
- **延迟**：输入侧去重（Current Paragraph 和 Sentence Ledger 部分重复）。预计只省几个百分点，且有影响译文的风险，等 M1/M2 后再评估。

## 10. 风险登记

| 风险 | 触发指标 | 影响 | 缓解 | 应急 |
|---|---|---|---|---|
| 去掉 alignment 后多句合并的段落对齐出错 | ALIGNMENT_FAILURE 增加 | 导出缺句 | 解析时校验覆盖，缺句直接拒收重试 | 回退老格式（兼容期内） |

| 价目规则再次变化 | 每周核对不一致 | 记账再次偏差 | 配置带核对日期 | 改配置，无需改代码 |

## 11. 禁止事项

- 不凭记忆写价格或时段（AGENTS.md）。只用价目页当日核实的值，并写明日期。
- 不为省钱关掉润色（它经过盲评验证）。
- 不悄悄改写历史 cost_usd：更正要另出对账单，并记录原值。
- 不用相似度代替质量判断。

## 12. 已知局限

- 本规格不能让"命中率"本身大幅提高；如果你看的指标是命中率，它基本不会变。
- 非高峰运行意味着白天提交的书可能要等几个小时才开始，最长到当天 10:00 UTC（北京时间 18:00）之后。
- 中国法定节假日按高峰计（多记），节假日的优惠这一版拿不到。
- 盲评需要人看，A/B 每次要花一些时间和少量费用（每章约 $0.2，按《The Art of AI》每章花费估）。
