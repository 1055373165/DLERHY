## 0. 一屏摘要

**最重要的 3 个发现**

1. **界面是按后端概念分页的，用户却只有一个对象：一本书（或一个网页）。** 7 个一级入口（WORK / RUNS / SHIP / ISSUES / APPROVE / LIB / MODELS，`src/components/AppLayout.tsx:63-71`）分别对应 run、export、issue、approval 这些内部表。最核心的路径「粘贴链接 → 读到中文」要点击约 9 次、切换 4 个页面，而且完成后没有任何「去阅读」的入口：阅读页只能从书库进（`LibraryPage.tsx:252`）。
2. **拖慢流程的不是机器，而是用户不知道轮到自己了。** 第一篇网页全程 42 分钟，其中约 28 分钟在等人：14.3 分钟停在「思考模式用光额度」的暂停上，14 分钟停在没人发现的审批上。用户守着页面时，人工等待只有 12–30 秒。审批数量只在打开「审批」页后才去查（`ApprovalsPage.tsx:60-63`），整个应用里没有任何全局提醒。
3. **首页是给审校团队的运营台，不是给读者的。** 工作台的主体是章节工作队列：优先级、指派筛选、记忆提案、待执行动作、时间线（`WorkspacePage.tsx:309-460`）。可是这些接口的写操作是 0 次，人工处理的审校问题是 0/65 条，章节指派 0 条，699 条记忆提案一直没人处理。与此同时，它们的两个查询在轮询流量里各占约 225 次，和运行、文档查询同一量级（§4 H1）。

**已死的假设**
- 「用户主要是下载译文」：已证伪。应用内阅读 18 次，纯下载 6 次，阅读占 75%（H3）。所以阅读页应该是终点，而不是书库里的一个次级按钮。
- 「审批流程本身慢，需要把后端改成事件驱动」：已证伪（上一轮会话实测）。最后一条审批通过后，0.1 秒就恢复运行；执行器本来就是事件唤醒、1 秒兜底轮询。慢是因为没人看见，不是因为系统慢。
- 「H2：大部分时间都在等人」：**只在有条件时成立**。用户没盯着页面时成立（67%），盯着时不成立（约 6%）。所以设计目标是「让离开页面的用户也能被叫回来」，而不是「减少审批」。

**M0 做什么（今天就能动手）**：修审计出的 8 项正确性缺陷（§1.3），重点是：
- 全局「需要你处理」标记；
- 运行完成后直达阅读；
- 阅读页隐藏当前部署做不出的格式；
- 界面里的英文文案全部改成中文；
- 出错时显示错误，不再伪装成空状态；
- 看不见的面板不再轮询。

**用户裁决（2026-09-20）**
1. **目标用户**：「所有对英文资源感兴趣、想快速读完中文版的人」。不是译者，也不是审校团队。主路径只有一条：粘贴链接 / 上传 → 等待 → 读中文。章节审校台、运行记录、问题清单、代理回合、术语与决策全部降到书页的「高级」区；首页和书页围绕「读」设计。
2. **信息架构**：接受大改，以书为中心，旧路由重定向。
3. **浏览器通知**：做，放在 M2。
4. **快速阅读模式**（2026-09-20）：做，默认开启；独立审查在 M1 前做（已做，§13.2）。

5. **上传后是否自动开始**（2026-09-20）：按费用上限决定。预估费用的上沿不超过用户设定的「自动开始上限」就自动开始，书页状态条显示本次预估并提供「停止」；超过上限，或拿不到价格（服务商没设单价），就停在书页，主按钮写「开始翻译（约 $x）」，并说明为什么没有自动开始。上限设为 0 等于每次都手动确认。上传前检查服务商；服务商配好后，自动恢复因 `provider.not_configured` 暂停的运行（决策 6）。

**按目标用户重排后的优先级**（详见 §9）：M0 先修「读者一定会撞上」的问题：完成后直达阅读、全局待审提示、中文文案、阅读格式按真实可用性显示、错误可见、隐藏面板不轮询。工作台内部的英文和审校台细节排在后面，因为读者基本看不到。

## 2. 问题定义

### 2.1 核心问题

一个付费用户（预付额度模式，见记忆 `pricing-prepaid-credit`）想读一本英文书或一篇英文网页的中文版。现在的界面需要他：
- 理解 run、export、issue、approval 这些内部概念；
- 在 4 个页面之间来回切换；
- 自己发现系统在等他。

结果是一次本来 3–6 分钟的转换被拖到 42 分钟，完成后还得自己去书库里找阅读入口。

**成功的定义**：用户只做三件事：把内容交给系统，在系统需要时给一个决定，读结果。这三件事都不需要知道任何内部概念，也不需要自己去找入口。

### 2.2 决策时刻

| 时刻 | 用户依据什么 | 做什么动作 | 现在的障碍 |
|---|---|---|---|
| 交付内容后 | 预计费用、预计耗时 | 点「开始翻译」 | 费用预估只在工作台显示，没有预计耗时；1/5 的文档上传后没开始 |
| 运行中被需要时 | 系统在等什么、选项分别意味着什么 | 批准或拒绝术语锁定；修服务商设置 | 没有提示（D5）；审批要跳到另一页 |
| 运行完成 | 结果好不好、有没有需要注意的问题 | 阅读；必要时处理问题、下载 | 没有阅读入口（D4）；质量摘要分散在「问题」页 |

### 2.3 北极星

**读到译文所需的人工阻塞时间与操作步数。**

- `人工阻塞占比 = Σ(运行处于「等人」状态的墙钟时间) / 运行墙钟时长`。「等人」指：暂停且原因属于 T12 列出的需要人处理的类别，或者代理在等审批。**不区分用户在场与否**（没有采集在场信号；v2 的在场/离场目标不可测，已删）。
  - 基线：run 3f3f46 为 67%（28.3 / 42.1 分钟），run 7691b4e7 约 6%，f7f45fbf 约 9%。
  - 目标：新运行的中位数 < 10%。快速阅读模式默认开启后，术语审批不再阻塞；剩余阻塞主要来自服务商配置和额度。
- `核心路径操作数 = 从粘贴链接到第一次读到中文的点击次数与页面切换次数`（粘贴本身不计）。
  - 基线：M0 后人工逐步核对为 5 + n 次点击（n = 需人工审批的条数）、3 次页面切换。M1 开工前由 `frontend/e2e/core_path.py` 实测（2026-09-20，M0 + 快速阅读模式）：**3 次点击（抓取 → 开始整书转换 → 阅读中文版）、1 次页面切换（/ → 阅读页）**。echo 服务商的代理不会锁定术语，所以这条测试走不到审批（n = 0）。
  - 目标（唯一目标）：费用在上限内时 ≤ 2 次点击（抓取 → 阅读），需要确认价格时 ≤ 3 次（抓取 → 开始翻译 → 阅读）；0 次离开书页。「页面切换」指离开 `/books/:id` 下的页面。

### 2.4 隐含需求

1. **离开页面也能被叫回来**（对应 D5、H2）。用户不会一直盯着一个 3–40 分钟的任务。
2. **界面上只出现用户的语言**（对应 D1、D2）。付费用户看到 `work_item.succeeded :: 1a01ca`，只会觉得这个产品没做完。
3. **不给注定失败的选项**（对应 D3）。当前部署做不出的格式，要么隐藏，要么禁用并说明原因。
4. **出错时说清楚错在哪、怎么办**（对应 D6，以及本会话里 405、500、PDF 这几次报错）。每个错误状态都要带下一步动作，比如跳到服务商页、重试。
5. **链接可以分享、可以刷新**（对应 T2）。以书为单位的 URL，刷新不丢状态，多个标签页互不干扰。

### 2.5 非目标

- 不做移动端原生应用，也不做完整的移动端适配。只保证 860px 以下可用，现有的抽屉式侧栏保留。
- 不做邮件或短信通知。浏览器通知是上限，关掉浏览器就收不到（§12）。
- 不重写后端的运行编排和审批机制。本次只加读模型，不改运行语义。
- 不引入重量级组件库（MUI、Ant 等）。沿用 CSS Modules 和设计变量（§5 决策 4）。
- 不删除章节审校台：降级为「高级」入口，而不是删掉（§5 决策 2）。
- 不做多人协作的实时编辑。

### 2.6 字面需求与诊断的分歧

- **字面需求**：「UI/UX 只是体验版本，用户使用起来不够流畅，彻底升级。」
- **诊断**：「流畅」的主要瓶颈不在视觉和交互细节，而在信息架构和提醒机制。H2 的数据显示，最长的阻塞来自用户不知道轮到自己；H1、H3 显示首页放的是没人用的功能，而最常用的阅读却藏在次级入口。

两边不冲突，但优先级不同。本规格按诊断排序：M0 修缺陷，M1 改信息架构，M2 做提醒机制，M3 才是视觉系统升级。用户已确认目标用户与信息架构方向（§0「用户裁决」）。

## 3. 设计哲学

### 3.1 失败考古

| 失败模式 | 表象 | 根因 | 诱因 | 早期信号 | 结构性防御 |
|---|---|---|---|---|---|
| 按数据库表分页 | 每个后端资源一个页面，用户在页面间搬运上下文 | 界面按实现者的心智模型组织 | 每加一个后端功能就顺手加一个页面，成本最低 | 一级导航超过 5 项；同一操作要跨页完成（本项目：7 项，审批要跨页） | 路由以用户对象为根（`/books/:id`）；新功能只能作为书页的一个标签或一个卡片加入 |
| 前端复刻后端状态机 | 界面显示的状态和真实状态不一致 | 同一套规则在两处实现，只改了一处 | 前端「顺手」自己推导状态 | 本会话实测：`stages` 字段改名半年没人发现 | 后端提供「书的当前处境」读模型（§6.4），前端只负责渲染，不再推导 |
| 提醒只在对应页面里 | 用户看不到系统在等他 | 把提醒当成页面内容，而不是全局状态 | 每个页面各管各的 | 运行里的等人时间远大于机器时间（H2） | 全局「需要你处理」计数，放在导航和标签页标题上；浏览器通知 |
| 轮询一切 | 请求量随面板数量线性增长 | 「多拉几次总没错」 | React Query 的 `refetchInterval` 太好写 | 看不见的面板也在请求（T4） | 查询只在其面板可见时启用；运行期间以 SSE 为主，轮询只做兜底 |
| 视觉大改一步到位 | 改完一堆回归，没法分阶段验收 | 把「彻底升级」理解成一次重写 | 视觉改动最容易被看见、被夸 | 一个 PR 改几十个文件，测试大面积失败 | 里程碑逐个上线；旧路由跳转到新路由；每个里程碑有可量化验收 |

### 3.2 平庸与顶尖的分界线

平庸的升级是换皮：换配色、换字体、加动画，页面结构不动。顶尖的升级先回答一个问题：「用户在这一刻要做哪一个决定？」然后让界面上只剩下做这个决定需要的东西，其他内容退到二级。在本项目里，这意味着：
- 运行中，最重要的是「它在等我吗」；
- 完成后，最重要的是「去读」；
- 章节工作队列、原始事件、代理回合这些内容全部退到「高级」或「运行记录」里。

### 3.3 范式转换：按后端资源分页 → 以书为中心

后面每个模块都能对应到这个转换：
- 路由：`/books/:id` 取代 `/runs`、`/deliverables`、`/issues`、`/approvals` 这几个依赖「当前文档」的页面；
- 读模型：`GET /documents/{id}/overview` 直接回答「这本书现在处在哪一步」；
- 导航：从 7 项减到 3 项（首页、需要你处理、设置）。

### 3.4 跨域移植

- **【工具借用】外卖/快递的订单页**：一个订单一个页面，顶部是一句话状态（「骑手已取餐，预计 12 分钟送达」），下面是时间线，异常时状态条变色并给出一个动作。借用的是「状态句 + 单一主操作 + 时间线」这个页面结构，不借用它的业务逻辑。
- **【隐喻】CI 流水线页**：用来帮助理解「阶段」的展示方式。只作隐喻，因为 CI 的用户是开发者，本产品的用户不是。

### 3.5 保留什么 / 丢弃什么

- **保留**：设计变量体系（`tokens.css`）、CSS Modules、React Query、SSE 接入（`runEvents.ts`）、阅读页的格式切换、服务商页、审批的后端机制、章节审校台（降级保留）。
- **丢弃**：一级导航里的 run、deliverable、issue、approval 这几个按后端概念划分的入口；主界面里的原始事件名和 id；`WorkspaceContext` 这个大一统 Provider；前端的阶段状态推导（改为读后端读模型）。

### 3.6 诚实的边界：本系统不是什么

- 不是翻译审校团队的协作平台：多人指派、队列优先级这些功能退为「高级」，本次不做增强。
- 不是桌面应用：浏览器关闭后收不到任何提醒。
- 不是所见即所得的译文编辑器：本次不支持在阅读页直接改译文。

## 5. 设计决策记录

**决策 1：以书为中心的信息架构**
- 选择：路由改为 `/`（新建 + 最近的书）、`/books/:id`（书页，含标签：概览 / 阅读 / 问题 / 术语与决策 / 运行记录 / 高级·逐章审校）、`/inbox`（跨书的「需要你处理」）、`/settings`（服务商、API key、额度）。旧路由 301 式重定向到新路由。
- 替代方案：保留现有 7 页，只做换皮和提醒。
- 理由：T1、T5、H2、H3。核心路径被 4 个页面切开，阅读入口藏在书库。
- 代价：路由和测试要大面积改；老用户需要重新熟悉。
- 逆转条件：M1 上线后，如果真实浏览器测得的核心路径点击数没有下降 ≥ 40%，就回退为「保留现有页面 + 全局提醒」。

**决策 2：章节审校台降级为「高级」标签，不删除**
- 选择：放到书页的「高级·逐章审校」标签下，默认折叠；它的查询只在标签打开时启用。
- 替代方案：删除；或者保持现状。
- 理由：H1 显示实际使用为 0；但样本只有一位用户，而且未来付费的专业译者可能会用，删掉以后恢复成本高。
- 代价：维护一个低使用率的界面。
- 逆转条件：6 周内写操作仍然是 0，就进入删除评审；每周写操作 > 0，就考虑把它提回概览页。

**决策 3：后端提供「书的当前处境」读模型，前端不再推导状态**
- 选择：新增 `GET /v1/documents/{id}/overview`，**不用单一枚举**，而是四个独立字段（§6.4）：
  - `readable`：是否已有中文版（merged 或 web 导出存在）；
  - `translation`：只看最近一次 `translate_full` 运行的状态；
  - `activity`：是否有导出等后台活动在进行；
  - `needs_you[]`：需要人处理的事项。

  各字段必须覆盖用户暂停、cancelled、draining、succeeded_with_warnings、从未开始这几种情况。
- **单一来源**：概览基于 `RunControlService` 的投影摘要（`_project_derived_stage_status`）构建，不再读原始缓存；暂停原因的说明表从前端 `runStopReason.ts` 移到后端，放在 `workers/failures.py` 旁边；`/inbox` 复用同一个构建函数；同一里程碑内删除前端的 `documentBadge`、`getPrimaryRunAction`、`stageStatus` 推导与 `runStopReason.ts`。
- 替代方案：单一枚举 `journey_state`（v2 的设计）。独立审查否决：能读的书会因为最新一次阅读触发的导出在运行或失败，被显示成「运行中」或「失败」（T10）。
- 理由：§1.4 第 3 条；T10、T11。
- 代价：多一个后端接口和契约测试；前端要同步删改三处推导。
- 逆转条件：无。这是正确性问题。

**决策 6：按费用上限自动开始**
- **选择**：
  - 抓取或上传成功后，前端取 `GET /documents/{id}/cost-estimate`（复用 `services/cost_estimate.py`）。按「可能扣的最多金额」判断：预付组织为 `cost_usd_range[1] × price_multiplier`，其他为 `cost_usd_range[1]`。这个值 ≤ 上限就用 `run_request.auto_started=true` 创建运行，否则等用户确认。
  - 没有 `cost_usd_range`（服务商没设单价）时一律不自动开始。
  - 上限是按浏览器保存的偏好，和快速阅读模式放在一起，在「设置 · 阅读偏好」里修改；书页等确认时写明当前上限并链到设置。
- **默认值 $1.00**：
  - 应用里的金额一律是美元（预估、月预算、预付余额），上限也用美元，免得换算不一致。
  - 实际花费以服务商设置的单价为准；本规格不写具体单价（v3.1 草稿里引用过凭记忆的 DeepSeek 单价，已删）。
  - 不依赖单价的事实：按本机两份文档的 token 预估（`GET /cost-estimate`），一篇网页（42 段）的输入上沿约 0.42M token、输出约 0.04M；一本 614 段的书约 4.3M 和 0.28M，大约是网页的 10 倍。所以无论单价多少，只要一整本书的预估超过 $1，一篇文章就只有它的十分之一左右。
  - $1 的意图是「文章通常自动开始，整本书通常先确认价格」，符合预付额度下「大额先确认」的原则。这个意图是否成立取决于服务商的单价：单价很低时整本书也可能低于 $1 而自动开始，单价很高时文章也要确认。上线后按真实单价和用户反馈调默认值。
- **替代方案**：
  - 始终自动开始：会在用户看到价格前扣费；
  - 始终手动：文章也要多点一次；
  - 上限存到组织设置：需要迁移，而且组织管理员不一定是读者本人。
- **理由**：用户裁决；§0 第 5 条；审查第 3 条。
- **代价**：上限存在浏览器里，换浏览器会回到默认值；自动开始的决定在前端做，只通过 API 创建的运行不会自动开始。
- **逆转条件**：多人共用一个组织、需要统一控制花费时，把上限挪到组织设置里。

**决策 4：不引入组件库，先补设计系统**
- 选择：在 `tokens.css` 上补字号梯度、暗色主题、动效变量；新增少量共享组件：`StateBanner`、`ActionCard`、`Timeline`、`Tabs`、`EmptyState`、`ErrorState`、`Skeleton`。
- 替代方案：引入 MUI、Ant 或 shadcn。
- 理由：现有代码零 UI 依赖，打包 328 KB（`08-frontend.md` §0）；页面数量少，自己维护的成本可控。
- 代价：自己写可访问性细节（焦点、ARIA）。
- 逆转条件：共享组件超过 15 个，或者可访问性审计有 ≥ 5 项不通过时，重新评估。

**决策 5：全局「需要你处理」计数 + 浏览器通知（需用户授权）**
- 选择：导航上显示红点和数量，标签页标题前加「(n)」；数据来自新接口 `GET /v1/inbox`，返回全部待审批和需要人处理的暂停。在书页里订阅 SSE 事件 `agent.approval.requested` 和 `run.paused`，收到时发浏览器通知（用户授权后才发）。
- 替代方案：只在书页内提示。
- 理由：H2。
- 代价：需要一个新接口；通知授权会打扰一次。
- 逆转条件：如果新运行的人工阻塞占比中位数没有降到 < 10%，就补做邮件通知（届时需要另开需求）。

## 6. 架构与模块

### 6.1 全景

```
/                 新建（上传 PDF/EPUB · 粘贴链接）＋ 最近的书（卡片，状态一句话 + 主操作）
/books/:id        顶部状态条 StateBanner（一句话 + 主操作 + 进度）
                  ├─ 概览：待你处理（就地审批卡片）· 时间线（人话事件）· 质量摘要 · 费用
                  ├─ 阅读：现有 ReaderPage（只列出当前部署做得出的格式）
                  ├─ 问题：现有 IssuesPage，限定在这本书
                  ├─ 术语与决策：BOOK.md + 术语表（从审批页移过来）
                  ├─ 运行记录：原始事件、代理回合、阶段明细（给技术用户）
                  └─ 高级·逐章审校：现有章节工作台（按需加载）
/inbox            跨书的待处理（审批 + 暂停），每项一个动作
/settings         服务商 · API key · 额度与花费
导航：首页 · 需要你处理 (n) · 设置      （书库 = 首页的「全部书」）
数据：GET /documents/{id}/overview、GET /inbox（新） + SSE（已有）→ React Query（每个功能一个 hook，替代 WorkspaceContext）
```

### 6.2 模块

| 模块 | 职责 | 输入 → 输出 | 失败降级 | 关键单测 |
|---|---|---|---|---|
| `useBookOverview(id)` | 取书的处境（读后端的 overview 接口） | id → overview | 接口报错时显示 `ErrorState`，附重试按钮 | §6.4 每种 `translation.state`，以及「可读但最新导出失败」各自渲染正确 |
| `StateBanner` | 一句话状态 + 唯一主操作 + 进度 | overview → UI | 没有预计剩余时间时只显示百分比 | 等待审批时的主操作是「处理 n 项」 |
| `ActionCard` | 就地审批、就地修复暂停 | 待处理项 → 批准 / 拒绝 / 跳转 | 提交失败时卡片内显示错误，不丢已填的备注 | 批准后卡片消失，运行恢复 |
| `Timeline` | 把事件翻译成人话 | 审计事件 → 句子 | 不认识的事件名进「运行记录」，不进时间线 | 所有 `EVENT_KINDS` 都有对应文案，或被显式忽略（与 `tests/test_frontend_event_kinds.py` 对齐） |
| `InboxBadge` | 全局待处理计数 | `GET /inbox`（有 SSE 时 30 秒轮询兜底） | 接口失败时隐藏计数，不显示 0 | 计数和标签页标题同步 |
| `Notifier` | 浏览器通知 | SSE 事件 → Notification | 未授权或不支持时静默 | 同一件事不重复通知 |
| `ReaderPage`（改） | 只列出可用格式 | capabilities → 标签 | —— | PDF 组件不可用时不出现 PDF 标签 |
| 文案层 `lib/copy.ts` | 集中管理状态、阶段、事件的中文文案 | 枚举 → 中文 | 未知值显示「其他（原值）」 | 界面文本里没有未登记的英文 |

### 6.3 数据模型

不新增表。`overview` 和 `inbox` 都是读模型，由现有的 `document_runs`、`approvals`、`run_audit_events`、`review_issues` 计算得出。

### 6.4 API 契约（新增）

- `GET /v1/documents/{id}/overview` →
  ```
  { readable: {ready: bool, formats: [...当前部署能读的格式]},
    translation: {state: "never_started" | "queued" | "running" | "paused" | "draining" | "succeeded" | "succeeded_with_warnings" | "failed" | "cancelled",
                  run_id, stop_reason, stop_reason_text, progress: {done, total}, eta_seconds | null},
    activity: {exporting: [export_type...]},
    needs_you: [{kind: "approval" | "paused", id, title, detail, action: {kind, target}}],
    quality: {open_issues, blocking}, cost: {spent_usd, estimate_usd | null} }
  ```
  - `translation` 只取最近一次 `translate_full`；导出运行的失败只体现在 `activity` 和对应格式上，不会把书标成失败。
  - `paused` 只有在原因属于 T12 的需人类别时才进入 `needs_you`；自动重试类原因只在 `translation` 里显示「正在重试」。
  - 错误：404 文档不存在（跨 org 也返回 404）。
- `GET /v1/inbox` → `{items: [...同 needs_you，另加 document_id、document_title], count}`，只列当前 org；用 `idx_approvals_document_status` 一次查询完成。
- `GET /v1/meta` 的 `capabilities: {pdf_renderer}`：M0 已实现。
- 以上都是只读接口，天然幂等。

### 6.5 展示原则

- 每屏只有一个主操作。
- 状态用一句话讲明白，例如「正在翻译，已完成 42/46 段，约 1 分钟」。
- 需要用户处理的事情，永远出现在书页最上方，同时在导航上计数。

## 8. 验证方法

### 8.1 评估目标

验证的是「用户能否不看说明就完成：交付 → 批准 → 阅读」，而不是页面美不美观。

### 8.2 指标

| 指标 | 公式 | 基线 | 目标 | 采集方式 |
|---|---|---|---|---|
| 核心路径操作数 | 从粘贴到阅读的点击数 / 页面切换数 | 5+n / 3（M0 后人工核对，M1 前由脚本复测） | 上限内 ≤ 2 / 0，需确认 ≤ 3 / 0 | `frontend/e2e/core_path.py`（Python Playwright；本地测试网页 `e2e/fixtures/article.html` + echo 服务商 + 临时 SQLite），每个里程碑跑一次 |
| 人工阻塞占比 | 见 §2.3（不分在场） | 67% / 6% / 9%（三次实测运行） | 新运行中位数 < 10% | `experiments.sh` 的 H2 段，统计之后每次真实运行 |
| 运行期间的请求量 | 单本书运行期间每分钟的 API 请求数 | 用 M0 前的日志计算 | 下降 ≥ 30% | 服务器日志 |
| 英文残留数 | 各页面渲染后可见文本中，不在白名单里的英文单词数 | D1 列出的 20 多处 | 0 | vitest 扫描（白名单：品牌名、格式名，如 Claude、Markdown、PDF、EPUB） |

### 8.3 协议

每个里程碑做前后对比：同一个网页、同一本测试 PDF（`.test-tmp/rsi/rsi-book.pdf`），用 echo 模型跑 Playwright 脚本。真实用户数据按上线日期切分，前后两段对比。

### 8.4 反自欺清单

- 点击数必须在真实浏览器里数，不能在 jsdom 里数；也不能只测网页，还要测多章节的 PDF。
- 人工阻塞占比没有在场信号可用，只能整体统计；报告时列出每次运行的值，不只给平均数（H2 的教训：在场与否差 10 倍）。
- 基线数据来自一位用户、约 2 天，不要把它当成付费用户的行为。上线后先用真实数据刷新基线，再判断目标是否达成。
- 英文残留扫描的白名单要人工审过，不能为了让测试通过去扩大白名单。

### 8.5 上线后健康监控

- `overview` 接口的错误率（静默产错探针：前端收到未知的 `translation.state` 时，上报到控制台并在界面上显示「其他」）。
- InboxBadge 的计数与 `approvals` 表 `pending` 行数定期对账。

## 9. 里程碑

- **最终一轮**：axe 0、键盘 0、样式与中文 0、版面 0（10 个页面 × 明暗，五个宽度）。
- **未做**：「高级区只在打开时发请求」没有实现——「更多」里的三个标签仍是路由，打开才加载对应组件，但组件的查询在路由进入时就发，没有额外的延迟加载；旧入口的重定向沿用 M1，未改动。

**快速阅读模式（2026-09-20 已实施，用户确认）**
- 后端：运行请求 `fast_reading=on` 时，在现有 `terminology_policy` 的 `AutoApproveRule` 列表末尾加一条 `auto.fast_reading_mode`，放在名称规则和高频规则之后，所以那两类仍记录各自原因。每条都照常写成 `auto_approved` 审批，`decided_by=auto.fast_reading_mode`。设置按运行生效，与其他代理选项一样放在运行请求里；API 或 CLI 不传时保持原行为。
- 前端：「开始整书转换」旁放开关，默认开启，记在浏览器里；文案说明代价。`createRun` 发送 `run_request.fast_reading`（审查第 4 条所说的缺口已补）。「审批」页新增「术语表」：列出每个锁定术语及锁定者（快速阅读模式 / 规则 / 人），可以修改或解锁，走 `GET/PUT /documents/{id}/terms`。M1 把它移到书页「术语与决策」标签。
- 测试：开启时不产生待审批、阶段一次完成；关闭时照旧停下（原有测试）；术语改与解锁的接口测试；前端开关默认值与请求体测试。

## 10. 风险登记

| 风险 | 触发指标 | 影响 | 缓解 | 应急 |
|---|---|---|---|---|
| 信息架构大改后，老用户找不到入口 | 上线后 404 或旧路由访问量上升 | 短期不适应 | 旧路由全部重定向；首次访问显示一次「新布局」提示 | 保留旧导航作为「经典视图」开关，一个版本后移除 |
| overview 读模型和运行时状态不一致 | 对账探针报错 | 界面状态错误 | 契约测试 + 与 `StageStatusCalculator` 共用逻辑 | 前端显示「状态获取中」，不做推断 |
| 基线来自单一用户，目标可能定错 | 上线后真实数据与基线差距很大 | 优化了错误的东西 | 上线后先刷新基线 | 重新定目标，不改设计方向 |

## 11. 禁止事项

1. **禁止前端推导阶段和运行状态**。理由：已证实会漂移（§1.4 第 3 条）；一律读后端读模型。
2. **禁止在主界面展示原始事件名、内部 id、英文枚举值**。理由：D1、D2；技术细节只放在「运行记录」标签里。
3. **禁止提供注定失败的选项**。理由：D3；做不出的格式要么隐藏，要么禁用并写明原因。
4. **禁止看不见的面板发请求**。理由：D9、T4。
5. **禁止出错时显示成空状态**。理由：D6；错误状态必须带原因和下一步动作。
6. **禁止为了本次升级删除章节审校台**。理由：决策 2 的逆转条件还没满足。
7. **禁止一次性大改后才验收**。理由：失败考古第 5 条；按里程碑逐个上线、逐个验收。

## 12. 已知局限

- **用户关掉浏览器，就收不到任何提醒。** 真正离开电脑的用户，仍然可能让运行卡在审批上几个小时。本规格不解决这个问题（邮件通知不在范围内）。
- **证据基础很薄**：一位用户（开发者本人）、约 2 天的日志、5 个文档。目标用户已由用户裁决为「快速读者」，所以「审校台没人用」和设计方向一致；但如果将来要服务专业译者，高级区需要重新评估。
- 以书为中心的设计会让「同时管理几十本书的运营人员」更难用：跨书视图只剩收件箱和书库列表。
- 预计剩余时间对 PDF 不可靠（结构审查、OCR 的耗时差异大），只能显示区间或只显示百分比。

## 13. 对抗记录（自我挑战，1 轮）

1. **[挑战 1] 针对决策 2，审校台降级**：付费的专业译者可能正是为逐章审校付费，降级会赶走高价值用户。
   - 失败场景：一位专业译者上线后找不到审校台。
   - 回应：【增强】「高级」标签在书页上可见，不隐藏；逆转条件是每周写操作 > 0 就提回概览页。H1 的样本只有一位用户，这一点已在 §12 写明。
2. **[挑战 2] 针对 §2.3，点击数基线是人工数出来的**，可能偏高，从而高估改进效果。
   - 回应：【采纳】H5 标为无法验证，M1 验收前必须用 Playwright 复测，并替换基线。
3. **[挑战 3] 针对决策 3，overview 读模型**会不会成为第二个状态机，和 `StageStatusCalculator` 漂移？
   - 失败场景：后端两处都在算状态，只改了其中一处。
   - 回应：【采纳】overview 必须调用 `StageStatusCalculator` 和运行计划，不自己推导；加契约测试。
4. **[挑战 4] 针对决策 5，浏览器通知**：用户拒绝授权后，提醒就只剩标签页标题；H2 的问题仍然存在。
   - 回应：【接受局限】写入 §12；以 M2 上线后的人工阻塞占比作为是否需要邮件通知的判断依据（决策 5 的逆转条件）。
5. **[挑战 5] 针对 M0 的「请求量下降 ≥ 30%」**：工作队列的两个查询约占运行期请求的三分之一，但 SSE 在线时的轮询本来就很稀疏，真实下降可能远小于 30%。
   - 回应：【采纳】验收时分别测量 SSE 在线和离线两种情况；如果在线时下降不足 30%，只要求离线场景达标。
6. **[挑战 6] 针对范式转换**：用户同时跑多本书时，以书为中心会不会让他在书页之间来回切换？
   - 回应：【增强】`/inbox` 负责跨书汇总；首页的「最近的书」卡片直接显示每本书的一句话状态和主操作，不必逐本点进去。

### 13.2 独立审查（2026-09-20，只读审查代理，未看设计理由）

| 发现 | 回应 |
|---|---|

## 14. 附录

- **默认参数**：
  - 收件箱在 SSE 在线时 30 秒兜底轮询，沿用现有「在线 15 秒 / 离线 2.5 秒」的思路，放宽到 30 秒，因为它不是运行进度（待校准：看实际通知延迟）；
  - 对比度 ≥ 4.5:1（WCAG AA 正文标准，【凭记忆·未核】，M3 实施时核实）。
