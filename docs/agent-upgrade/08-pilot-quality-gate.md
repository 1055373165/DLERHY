# 08 · 设计：试译关卡（前两章试译 → 分层质检 → 修复循环 → 全书翻译）

> 状态：设计稿，待用户确认（2026-09-25）。来源：两本 Manning PDF 各自暴露出不同的解析问题，靠人工一轮轮修复（`fix/pdf-structure`、`fix/pdf-structure-2`、`fix/figure-crops`、`fix/no-export-hints`）。用户决定把这个过程产品化，交给 agent 按问题类型自动选择修复路径，只有修不掉时才交给人。本篇定义流程、各层检查、修复工具箱、「这本书特有 vs 系统性」的判定，以及经验账本。

## 1. 已确认的决策（2026-09-25，用户）

| 议题 | 决策 |
|---|---|
| 试译范围 | **前两章**（第一章通常是导论，暴露不出代码、表格、复杂图表的问题），走完整流程后把最终效果交给用户 |
| 收费 | **质量优先，不满意不要钱**：试译免费，用户看过试译后自主决定是否付费翻译全书；预付额度只在全书运行时扣除 |
| 修复方式 | 质检 agent 分层审查，修复 agent 判断问题是这本书特有还是系统性：特有问题走这本书的专属路径，系统问题修复后重译；直到没有严重问题才开全书并行翻译 |
| 持续进化 | 每本书的问题、分类、修复方式和效果都要记录，后来的书从前面的书学到的东西出发 |
| 译文纯净 | 译文里只出现原文的译文，不出现「图片锚点保留」之类的程序提示（已由 `fix/no-export-hints` 修复） |

## 2. 设计约束（为什么这样设计）

1. **运行中不改代码。** 之前删掉的运行时自修复层（生成补丁、打包、下发）失败的原因，是在运行时改代码、无法验证和回滚（见 `docs/refactor/PLAN.md`）。本设计中 agent 只能用**封闭、可逆、可验证**的工具修改**这本书的结构数据与翻译设置**；代码层面的修复走开发流程（§7）。
2. **先免费、后花钱。** 能用规则免费发现的问题（解析体检），不拿翻译去发现。
3. **同一套传感器既判断问题、又验收修复。** 修复有没有用，由同一套检查在修复后重跑来判定；指标变好、且没有别的指标变差才保留，否则撤回。
4. **只重译受影响的包。** 修复循环不整章重译。
5. **有边界。** 轮数、预算、时间都有上限；到了上限仍有严重问题就交给用户，并附上页面截图和一个明确的问题。

## 3. 流程总览

```
导入 ─→ G1 解析体检（规则，免费）──有异常──→ 修复 agent（结构类工具）──→ 复检
          │                                                          │
          └──────────────── 通过 ←───────────────────────────────────┘
                              │
                     G2 试译：前两章，完整流程（术语 → 翻译 → 润色 → 审校 → 导出）
                              │
                     G3 分层质检（规则 + 视觉 + 模型）
                              │
                 有严重问题 ──┴── 无严重问题 ─→ 把试译效果交给用户
                     │                              │
            G4 修复 agent：分类 + 选路径              用户选择：付费翻译全书 / 放弃
                     │                                   │
          只重译受影响的包 → 回到 G3                 G5 全书并行翻译（沿用专属路径）
          （达到轮数/预算上限 → 需要你处理）
```

## 4. G1 解析体检（规则，零模型成本）

导入后立即运行，结果写入这本书的体检报告，书页上可见。每项都有阈值与严重程度；**全部来自这两本书实际遇到的问题**。

| 检查项 | 做法 | 严重程度 | 出处 |
|---|---|---|---|
| 章节与书签一致 | 有 PDF 书签时，逐条比对章节切分；目录页条目不得成章；Part 下的章要成章 | 严重 | RAG 书：目录条目成章、正文按 Part 合并 |
| 章节命名合理 | 章节标题不得是「References」「Index」等而内容是正文；标题不得带页码 | 严重 | RAG 书「References」装了第 1–2 章 |
| 前言分节 | 书签里的一级前言条目各自成节 | 一般 | Agent 书前言并入致谢 |
| 异常字符 | 块首的 `¡`、U+FFFD、私用区字符比例 | 严重 | RAG 书 502 处 `¡` |
| 伪标题 | 等宽字体、以 `#` 开头的「标题」 | 一般 | RAG 书 101 处代码注释成标题 |
| 断行单词 | 行尾连字符/软连字符残留，按本书自身证据判定 | 一般 | 两本书各约 500 处 |
| 图片区域 | `figure_region_problems`：区域压到页眉页脚、切断线条或标注、含图注 | 严重 | 图 1.4/1.5/1.6 |
| 碎片与空白图片 | 宽或高小于阈值的图片块；无内容的图片块 | 一般 | RAG 书 756 个碎片图片 |
| 图注混入正文 | 导出层把后续正文并进图注 | 严重 | 图 1.2 |
| 重复文字 | 图中标注又以正文段落出现 | 一般 | 两本书若干页 |

输出：每项的计数、样例（页码 + 截图）、严重程度。**有严重项就先修，不进入试译。**

## 5. G2 试译

- 范围：前两章（按章节识别结果，前言/Part 页不算）。
- 走**完整流程**：术语阶段、翻译、润色、模型审校、规则审校、导出。只有这样看到的效果才代表全书。
- 成本：两本书实测为全书的 10%–15%，约 $0.12–0.17（DeepSeek flash 低峰价）。由我们承担。

## 6. G3 分层质检

按影响阅读的程度分层，逐层检查；前一层的严重问题会影响后一层的判断，所以按顺序执行、分层汇报。

| 层 | 检查什么 | 怎么查 | 由谁执行 |
|---|---|---|---|
| L1 结构 | 章节、标题层级、目录、前言 | 规则（复用 G1）+ 导出后的目录 | 规则 |
| L2 图表 | 图片完整、清晰、没被切、没多框进页眉；图注配对 | 规则 + 渲染截图看图 | Export QA agent（视觉） |
| L3 表格 | 行列完整、表头、跨页表 | 规则 + 截图 | Export QA agent |
| L4 代码与格式 | 代码块完整、代码没被翻译、行内代码样式、列表、脚注、公式 | 规则 | 规则 |
| L5 术语 | 同一术语前后一致（如「代码清单」与「清单」）、锁定术语遵守率 | 规则（`find_term_violations`）+ 统计 | 规则 |
| L6 忠实度 | 漏译、错译、比较级/否定/因果被改 | 抽样 | Reviewer agent |
| L7 排版与纯净 | 中英混排空格、标点、内部标记与程序提示泄漏、残留英文 | 规则 | 规则 |

严重程度统一为三级：

- **阻断**：读者无法正常阅读或会被误导（章节错乱、图被切、正文进了图注、意思译反）。有阻断项不能交付试译。
- **一般**：明显影响观感但不误导（术语不统一、断行单词、多余空格）。
- **轻微**：个别瑕疵。

## 7. G4 修复 agent

### 7.1 分类：这本书特有，还是系统性

对每个问题按下面的顺序判断（前一条成立就停止）：

1. **经验账本里有同类记录**，且当时判为系统性且已在代码中修复 → 这次复发说明修复不完整，按**系统性**处理，并关联原记录。
2. **同一类问题在账本里已出现在 ≥2 本书中** → **系统性**。
3. **问题的原因可以用通用规则描述**（例如「符号字体的项目符号被解码成 ¡」「Part 下的章没有成章」），不依赖这本书的具体文字 → **系统性（候选）**。
4. 其余（这本书特有的版式、个别页面的奇怪排版、出版社的特殊约定）→ **这本书特有**。

### 7.2 修复工具箱（封闭集合）

| 工具 | 修什么 | 可逆 | 权限 |
|---|---|---|---|
| 切换/叠加解析修复选项（`recovery_skills`） | 这本书需要的解析策略 | 是 | 自动 |
| 以 PDF 书签为准重新切分章节 | 章节错乱 | 是（解析版本分叉） | 自动 |
| 结构修改（改块类型、合并、拆分、图注挂接） | 个别块识别错 | 是 | 自动，批量超过阈值需审批 |
| 图片区域覆盖（手动区域） | 个别图裁剪错 | 是 | 自动 |
| BOOK.md 翻译说明（专属提示） | 这本书特有的译法、格式约定 | 是 | 自动 |
| 术语表修改 | 术语不统一 | 是 | 已有规则（快速模式等） |
| 重译指定包 | 以上修复后的译文刷新 | 是 | 自动，受预算约束 |

每次修复后：重跑相关检查 → **只有指标变好、且没有其他指标变差才保留**，否则撤回并尝试下一条路径。

### 7.3 系统性问题的处理

1. 先给这本书一条**绕行路径**（上面工具箱中的某一项），让试译不被卡住。
2. 生成**缺陷单**：问题描述、证据（页码、截图、块数据）、复现方法、推测原因、影响范围。
3. 缺陷单交给**开发侧**编码 agent，在独立分支上修复；必须通过真实书样本库回归（§9）；由用户批准合并。
4. 合并后，受影响的书可以选择按新代码重新解析、重译受影响的包。

### 7.4 循环边界

- 最多 3 轮修复；试译预算上限为「试译预估成本 × 2」；
- 达到上限仍有阻断项 → 进入「需要你处理」，附截图和一个明确的问题（例如「第 138 页这张图由细线构成，自动识别失败。要把它当作图片保留原样吗？」）。

## 8. 经验账本

每本书、每个问题记一条：

| 字段 | 说明 |
|---|---|
| 书、出版社、PDF 生产工具 | 用于预测相似书的问题 |
| 检查层与问题类别 | 例如 L2 / `figure_region.header_band` |
| 证据 | 页码、截图、块 ID |
| 分类 | 特有 / 系统性，及判定依据（§7.1 第几条） |
| 采用的修复路径 | 工具箱中的哪一项，参数 |
| 结果 | 修复后指标、是否反复 |
| 关联缺陷单 / 代码提交 | 系统性问题的去向 |

用途：

- **导入新书时**：按出版社和生产工具查账本，把高发问题列为体检重点；
- **修复 agent 选路径时**：优先在同类问题上成功过的路径；
- **升级规则**：同一类「特有问题」在 ≥2 本书出现，自动升级为系统性候选；
- **衡量进化**：跟踪「试译一次通过率」「每本书阻断问题数」「每本书修复轮数」随时间的变化。

## 9. 真实书样本库

- PDF 文件留在用户硬盘，不进仓库（版权），样本库只登记路径与期望：章节数、章节标题、各项体检指标的上限。
- 当前样本：RAG 书、Build an AI Agent。每本出过问题的书都登记进来。
- 回归方式：与 PostgreSQL 测试相同，按环境变量开启（例如 `BOOK_AGENT_RUN_CORPUS_TESTS=1`），逐本解析、比对期望。**解析代码的任何修改都必须跑样本库。**

## 11. 分阶段实施

| 阶段 | 内容 | 验收 |
|---|---|---|
| Q1 体检 | G1 全部检查项；导入后自动运行；书页显示报告 | 两本书修复前的数据能复现 §4 的问题；修复后全部通过 |
| Q2 样本库 | 清单、回归入口、这两本书的期望值 | 解析代码回退到修复前，回归必须失败 |

| Q4 分层质检 | L1–L7 检查，严重程度，分层报告 | 用这两本书的已知问题做测试样本，检出率 100% |
